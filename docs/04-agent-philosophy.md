# Agent 设计理念

> 确定的动作用按钮，不确定的方向用对话。
>
> Agent 是创作的辅助助手，不是系统的操作者。

---

## 一个核心判断

大多数 AI 工具的问题是把 Agent 做成了「万能入口」——什么都通过对话完成，建项目、改设置、调布局、生成内容、导出数据。用户看起来在和 AI 聊天，实际上在学一套新的指令语法。

Craft 的做法是反过来想：**哪些事情用户已经知道该怎么做，只是需要 AI 帮忙想想方向？哪些事情用户需要明确的按钮和表单，而不是对着对话框猜？**

答案很清晰：

- **确定的动作**（保存、导出、建表、改布局、交付打包）→ 按钮和表单
- **不确定的方向**（接下来写什么、这周进展怎样、素材利用率如何）→ 对话

---

## Agent 适合做什么

Agent 的能力边界由一个原则决定：**读数据给判断，不代替按钮做动作。**

适合交给 Agent 的事：

- **复盘**：项目推进到哪了？哪些素材还没用上？里程碑达成了没有？
- **探索**：这些素材之间有什么关联？有没有我遗漏的角度？
- **参谋**：我卡住了，能给我一些方向建议吗？
- **答疑**：我之前采过关于这个主题的内容吗？上次做到哪了？

这些事有一个共同点：它们都需要**读已有数据并给出判断**，而不是替用户做一个确定性的操作。

---

## Agent 不适合做什么

不适合交给 Agent 的事：

- **建表、改布局、配置数据流**：这些是确定性动作，用户需要的是可预期的界面操作，不是对话里的模糊指令
- **交付打包**：导出什么格式、包含哪些内容、目标平台是什么——这些需要明确的表单选择，不是聊天能解决的
- **代替用户做决策**：AI 可以建议，但「这个项目完成了」「这条素材要保留」这种判断应该由用户自己做出

判断标准很简单：**如果这个动作有明确的对错，用按钮；如果这个动作需要思考和判断，用对话。**

---

## Agent 的感知范围

Agent 能帮多少忙，取决于它能读到多少上下文。

在 Craft 的设计里，Agent 的感知和项目数量直接相关：

- **Free 用户（最多 3 个项目）**：Agent 能读取这 3 个项目的上下文——素材、日志、创作记录、交付历史。足够在单项目或小规模联动中给出有价值的建议。
- **Creator 用户（无限项目）**：Agent 能感知所有项目的完整上下文，建立跨项目关联。比如你在写小说，Agent 能同时看到你之前短剧项目的复盘结论，提醒你「上一部作品里这个角色没立住，这次可以注意」。

这不是功能限制，是上下文深度的差异。Free 用户的 Agent 是「项目助手」，Creator 用户的 Agent 是「创作生态顾问」。

---

## AI 在创作循环中的位置

回到资产的定义（[五层创作模型](./01-five-layers.md)）：成品、过程碎片、创作记录都是资产。AI 在这个循环里是**读者，不是作者**：

1. **读事实，给判断**：AI 读沉淀的素材、日志、交付记录，基于事实给出复盘与建议。它不创造事实，只解读事实。
2. **判断也是资产**：AI 的结论（复盘、建议、洞察）作为**判断层**沉淀，带来源标注——什么时间、由哪个模型生成。判断层与事实层分开，AI 说了什么、人做了什么，永远分得清。
3. **不碰事实链**：AI 不修改、不补写创作记录。事实链只记录人的行为；判断错了可以改、可以清，事实保持原样。

这保证了闭环的干净：复盘的结论回流成下一轮创作的灵感（复盘 → 采集），但每一步判断都有出处，每一条事实都未被污染。

## BYOK：用户掌握主动权

Craft 不内置 AI 模型，不向用户收 AI 费用。用户配置自己的 API Key（OpenAI、Claude 等），直接付给模型服务商。

这个设计出于三个考虑：

1. **用户不应该被绑定在平台的 AI 能力上**。如果你的 AI 体验依赖于平台内置的模型，你就被锁死了。BYOK 让你随时可以换模型、换服务商。
2. **平台没有理由在中间加价**。用户自带 Key，模型服务商直接收费，我们不做 AI 二道贩子。
3. **AI 是辅助能力，不是付费门槛**。把 AI 锁进付费版，挡住的正是认真创作的人；而日志链是创作者自己的积累，理应属于创作者，不该成为工具的筹码。

---

## 一句话总结

Agent 的价值不在于它能替你做多少事，而在于它**基于你的创作过程，帮你看见你自己看不见的东西**。
